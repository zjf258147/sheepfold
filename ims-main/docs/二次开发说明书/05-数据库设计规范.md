
生成的连接串：`mysql+pymysql://ims:ims_pass@localhost:3306/ims?charset=utf8mb4`

### 5.2.2 连接池配置

[backend/app/db/database.py](file:///c:/Users/25075/Desktop/IMS生产物料与产品追溯管理系统/ims-main/backend/app/db/database.py)：

| 参数 | 值 | 说明 |
|------|-----|------|
| `pool_pre_ping` | `True` | 每次获取连接前 `SELECT 1`，防止使用已断开的连接 |
| `pool_recycle` | `3600` | 连接超过 1 小时回收，避免 MySQL `wait_timeout` |
| `pool_size` | `10` | 连接池大小 |
| `max_overflow` | `20` | 超出 pool_size 时最多额外创建 20 个连接 |
| `echo` | `settings.DEBUG` | DEBUG 模式时打印 SQL |

### 5.2.3 FastAPI 依赖注入

```python

@router.get("")
def list_items(db: Session = Depends(get_db)):
    ...
```

> ⚠️ FastAPI 在每个请求结束后自动关闭 Session。不要在业务代码中手动创建/关闭 Session。

## 5.3 表设计规范

### 5.3.1 必备字段

每个业务表都从 `TimestampMixin` 继承，因此自动包含以下字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `created_at` | `DateTime` | 创建时间，由 `server_default=func.now()` 自动填充 |
| `updated_at` | `DateTime` | 更新时间，由 `onupdate=func.now()` 自动更新 |

> 这两个字段由数据库自动维护，不应在业务代码中手动赋值。

### 5.3.2 主键规范

统一使用 `BigInteger` + 自增：

```python
id: Mapped[int] = mapped_column(BigInteger, primary_key=True, autoincrement=True)
```

> ❌ 不要使用 `Integer` 作为主键类型——`Integer` 上限约 21 亿，高并发场景下有溢出风险。

### 5.3.3 字段类型速查

| 业务场景 | 列类型 | 示例 |
|---------|--------|------|
| 短文本（≤255） | `String(N)` | `String(100)` |
| 中文本（≤500） | `String(N)` | `String(500)` |
| 长文本/富文本 | `Text` | `Text` |
| 整数 | `Integer` | `Integer` |
| 大整数、ID | `BigInteger` | `BigInteger` |
| 金额 | `Numeric(12, 2)` | 12 位，2 位小数 |
| 日期时间 | `DateTime` | `DateTime` |
| 布尔 | 不推荐 | 用 `String(1)` 或 `Integer` 代替 |
| JSON | 不推荐 | 用关联表代替 |

> ⚠️ 不要使用 MySQL 的 `TINYINT(1)` 布尔类型，它在 SQLAlchemy 中有类型映射问题。用 `Integer` 或 `String` 代替。

### 5.3.4 外键强制

所有表间关联必须使用 `ForeignKey`：

```python
partner_id: Mapped[int] = mapped_column(
    Integer, ForeignKey("partner.id"), nullable=False
)
```

> 好处：Alembic autogenerate 能正确生成外键约束，防止脏数据。

### 5.3.5 索引策略

索引加在该列上可为查询加速。必加索引的场景：

| 场景 | 示例 |
|------|------|
| 外键列 | `ForeignKey("partner.id"), index=True` |
| 唯一字段 | `unique=True, index=True`（唯一约束自带索引） |
| 状态列（高频筛选） | `index=True` |
| 时间列（范围查询） | 按需添加 |
| 模糊搜索列 | 在查询中使用 `LIKE` 的列 |

> ⚠️ 不要给每个列都加索引——索引虽加速查询，但会降低写入性能和占用磁盘。只给高频筛选列加。

### 5.3.6 comment 必须写

所有 `mapped_column` 必须写 `comment`，因为 `generate_data_dict.py` 依赖它生成数据字典：

```python
order_no: Mapped[str] = mapped_column(
    String(30), unique=True, nullable=False, comment="入库单号（JIN-开头）"
)
```

> 没有 `comment` 的列在数据字典中显示为空，导致可读性下降。

## 5.5 Alembic 迁移规范

### 5.5.1 配置

[backend/alembic/env.py](file:///c:/Users/25075/Desktop/IMS生产物料与产品追溯管理系统/ims-main/backend/alembic/env.py)：

- 自动使用 `.env` 中的数据库配置
- 自动导入所有 models（`import app.models`），确保 autogenerate 能发现所有表
- 配置了 `compare_type=True`，能检测列类型变更

### 5.5.2 生成迁移

```bash
$ cd backend

# 生成自动迁移文件
$ uv run alembic revision --autogenerate -m "描述性的变更说明"

# 执行迁移
$ uv run alembic upgrade head

# 回滚一步
$ uv run alembic downgrade -1
```

### 5.5.3 迁移文件命名

```
backend/alembic/versions/
├── 001_initial.py
├── 002_add_incoming_tables.py
├── 003_add_rma_tables.py
└── ...
```

> 文件名遵循 `序号_描述.py` 格式。序号确保按时间顺序递增。

### 5.5.4 迁移安全规则

| 规则 | 说明 |
|------|------|
| ✅ 生成后必须检查 | `--autogenerate` 可能遗漏或生成错误的迁移 |
| ❌ 不要在生产环境回滚 | 能向前兼容就用新的迁移修，不回滚已有的 |
| ❌ 禁止手动改已执行的迁移 | 已经执行的迁移不能修改，新增迁移修复 |
| ✅ 危险操作需手动确认 | `DROP TABLE`、`ALTER COLUMN` 等不会自动生成 |

### 5.5.5 修改字段后生成迁移示例

```bash
# 1. 修改模型（如添加字段）
# 2. 生成迁移
$ uv run alembic revision --autogenerate -m "add remark field to inbound_order"
# 3. 检查生成的文件
# 4. 执行迁移
$ uv run alembic upgrade head
# 5. 重新生成数据字典
$ uv run python scripts/generate_data_dict.py
```

> 💡 每次修改表结构后，务必重新运行 `generate_data_dict.py`。

## 5.6 查询优化

### 5.6.1 N+1 问题

**问题代码**（每条 order 触发一次 partner 查询）：

```python
orders = db.query(InboundOrder).all()
for order in orders:
    print(order.partner.name)  # ← 每次都查一次 partner
```

**正确写法**（使用 `joinedload` 预加载）：

```python
orders = db.query(InboundOrder).options(
    joinedload(InboundOrder.partner)
).all()
```

### 5.6.2 避免 `SELECT *` 的代价

当只需要部分列时，用 `with_entities` 或只加载需要的关联：

```python
# 只查需要的字段
names = db.query(InboundOrder.order_no).filter(InboundOrder.status == "ACTIVE").all()

# 列表页不需要全部关联
query = db.query(InboundOrder)  # 不预加载 heavy 关联
```

> 💡 项目中使用 `lazy="select"` 作为默认关联策略——对于列表查询只加载主数据，详情页时才自动加载关联。

### 5.6.3 分页基准写法

```python
def get_orders(db: Session, page: int = 1, page_size: int = 20, ...):
    query = db.query(InboundOrder)
    # ... 筛选条件

    total = query.count()
    items = query.order_by(InboundOrder.id.desc()) \
                 .offset((page - 1) * page_size) \
                 .limit(page_size) \
                 .all()
    return total, items
```

## 5.7 数据字典维护

### 5.7.1 自动生成

修改表结构后，运行脚本自动更新数据字典：

```bash
$ cd backend
$ uv run python scripts/generate_data_dict.py
```

生成文件：[docs/附录/数据字典.md](file:///c:/Users/25075/Desktop/IMS生产物料与产品追溯管理系统/ims-main/docs/附录/数据字典.md)

### 5.7.2 脚本原理

`generate_data_dict.py` 遍历所有 SQLAlchemy 模型，提取每个表的字段、类型、注释、默认值，按业务模块分组输出。

| 参数 | 说明 |
|------|------|
| `--output` | 输出路径（默认 `../docs/附录/数据字典.md`） |
| `--group-by` | 分组方式（`module` / `table`，默认 `module`） |

### 5.7.3 模块映射

脚本通过 `TABLE_OVERRIDE` 维护模块归属：

```python
TABLE_OVERRIDE = {
    # model_cls → module_name
    "InboundOrder": "入库管理",
    "InboundOrderLine": "入库管理",
    ...
}
```

> 新增表时，在 `TABLE_OVERRIDE` 中添加映射，确保数据字典中归属正确的模块。

## 5.8 常见设计模式

### 5.8.1 主-子表模式

入库单、出库单等采用主-子表结构：

```
InboundOrder (主) ──1:N── InboundOrderLine (商品行)
                           └── 1:N ── InboundOrderItem (SN单品)
```

- **主表**记录订单级别信息（单号、状态、往来单位）
- **行表**记录商品级别信息（SKU、数量、单价）
- **单品表**记录 SN 级别信息（每个 SN 的绑定）

> 新增类似模块时，参照此三层结构。

### 5.8.2 状态机模式

每个单据/单品遵循固定的状态流转。状态变更由 service 层的审核/操作函数统一管理，状态值通过枚举约束。

> 详见《系统说明书》第6.1节"核心状态机"了解各业务线的状态流转图。

### 5.8.3 软删除模式

系统中一般不物理删除数据，而是通过状态字段标记：

- 单据取消：`operation_status = CANCELLED`
- 返回退库：通过 `RETURNED_FROM_*` 标记库存属性

> 新增功能时优先使用状态标记而非物理删除。
