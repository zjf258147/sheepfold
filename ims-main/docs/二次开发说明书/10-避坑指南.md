## 10.1 数据库相关

### 10.1.1 不要手动调用 `db.commit()`

❌ **错误做法**：

```python
def create_order(db: Session, ...):
    order = InboundOrder(...)
    db.add(order)
    db.commit()  # ← 不要这样做！
```

✅ **正确做法**：FastAPI 在请求结束时自动提交。如果需要在 service 中立即获取 ID，使用 `db.flush()`：

```python
def create_order(db: Session, ...):
    order = InboundOrder(...)
    db.add(order)
    db.flush()  # 立即写入获取 ID，但事务未提交
    # 使用 order.id 创建关联记录
```

**原因**：手动 `commit()` 会导致上层无法回滚异常。如果 service 已 commit，但在 api 层发生异常，前面的 commit 无法回滚。

### 10.1.2 大结果集必须分页

❌ **错误做法**：

```python
all_items = db.query(InventoryItem).all()  # 可能返回百万条
```

✅ **正确做法**：

```python
items = db.query(InventoryItem).offset((page - 1) * page_size).limit(page_size).all()
```

**原因**：当前系统使用 `JSON` 序列化，大结果集会导致 OOM 或超时。

### 10.1.3 N+1 查询是性能杀手

❌ **错误做法**：

```python
orders = db.query(InboundOrder).all()
for order in orders:
    print(order.partner.name)  # ← 每个 order 都会查一次 partner
```

✅ **正确做法**：

```python
orders = db.query(InboundOrder).options(
    joinedload(InboundOrder.partner)
).all()
```

**原因**：默认 `lazy="select"` 在访问关联时才会发 SQL。列表页不加 `joinedload` 会导致 N+1 查询。

### 10.1.4 枚举值用大写字符串，不用数字

❌ **错误做法**：

```python
class Status(str, enum.Enum):
    ACTIVE = "1"
    DISABLED = "2"
```

✅ **正确做法**：

```python
class Status(str, enum.Enum):
    ACTIVE = "ACTIVE"
    DISABLED = "DISABLED"
```

**原因**：数字枚举在数据库和日志中不可读。"1" 和 "2" 在半年后没有人记得含义。

## 10.2 ORM 相关

### 10.2.1 模型修改后必须生成迁移

❌ **错误做法**：修改 `models/*.py` 后不运行迁移，期望 SQLAlchemy 自动建表。

✅ **正确做法**：

```bash
$ uv run alembic revision --autogenerate -m "描述"
$ uv run alembic upgrade head
```

**原因**：生产环境不会 `create_all()`。所有表结构变更必须通过 Alembic 迁移。

### 10.2.2 `mapped_column` 的 `nullable` 默认行为

SQLAlchemy 2.0 中，`Mapped[str]` 默认 `nullable=True`，`Mapped[str | None]` 也是 `nullable=True`。

必须显式设置 `nullable=False` 来创建 NOT NULL 约束：

```python
# 可为空（默认）
remark: Mapped[str | None] = mapped_column(String(500), nullable=True)

# 不可为空
name: Mapped[str] = mapped_column(String(100), nullable=False)
```

> ⚠️ 忘记写 `nullable=False` 是最常见的 schema bug，Alembic 会自动检测但最好一次写对。

### 10.2.3 Pydantic Schema 必须设置 `from_attributes`

```python
class MyResponse(BaseModel):
    id: int
    name: str

    model_config = {"from_attributes": True}  # ← 必须！
```

**原因**：不加 `from_attributes` 会导致 `model_validate(orm_object)` 报错。

## 10.3 API 相关

### 10.3.1 响应用 `R<T>` 包装，不要裸返回

❌ **错误做法**：

```python
return {"id": 1, "name": "test"}
```

✅ **正确做法**：

```python
return R.ok(data={"id": 1, "name": "test"})
```

**原因**：前端拦截器依赖 `{code, msg, data}` 结构。裸返回会导致前端报 `code !== 0` 的通用错误。

### 10.3.2 `response_model` 中的泛型必须完整

❌ **错误做法**：

```python
@router.get("", response_model=R)
```

✅ **正确做法**：

```python
@router.get("", response_model=R[PageResult[MyResponse]])
```

**原因**：不写泛型参数，Swagger 文档不会显示数据结构。前端也无法通过类型推导获取字段。

### 10.3.3 权限检查不要漏

❌ **错误做法**：

```python
@router.post("")
def create_item(db: Session = Depends(get_db)):  # ← 没有用户检查！
```

✅ **正确做法**：

```python
@router.post("")
def create_item(
    db: Session = Depends(get_db),
    current_user: User = Depends(get_current_user),
):
```

> ⚠️ 最容易被遗忘的是"已登录即可"的场景。至少加 `Depends(get_current_user)` 确保用户已认证。

## 10.4 前端相关

### 10.4.1 API 调用返回值已解包

```javascript
// API 返回 { code: 0, msg: "success", data: {...} }
// 拦截器已处理，调用方拿到的就是 R 对象
const res = await listItems(params)
// res.data 是实际数据（拦截器把 axios response.data 返回了）
// 所以：res.data.items，不是 res.data.data.items
```

> ⚠️ 这是新手最容易写岔的地方。放一个 console.log 确认数据结构。

### 10.4.2 删除/危险操作必须先确认

❌ **错误做法**：

```javascript
async function handleDelete(row) {
  await deleteFaq(row.id)
  ElMessage.success('删除成功')
}
```

✅ **正确做法**：

```javascript
async function handleDelete(row) {
  try {
    await ElMessageBox.confirm(`确定删除吗？`, '确认', { type: 'warning' })
    await deleteFaq(row.id)
    ElMessage.success('删除成功')
    fetchData()
  } catch { /* 用户取消 */ }
}
```

### 10.4.3 `v-model` 绑定对象要创建副本

❌ **错误做法**：

```javascript
// row 是表格当前行的引用，修改表单会直接影响表格显示
form.value = row
```

✅ **正确做法**：

```javascript
form.value = { ...row }  // 浅拷贝
// 或
form.value = JSON.parse(JSON.stringify(row))  // 深拷贝（有嵌套时）
```

### 10.4.4 枚举值必须与后端一致

前端 `enums.js` 中的键名必须与后端 `enums.py` 中枚举的 `.value` 一致：

```python
# 后端
class Status(str, enum.Enum):
    INITIATED = "INITIATED"
    APPROVED = "APPROVED"
```

```javascript
// 前端
export const STATUS_MAP = {
  INITIATED: '已发起',   // ← key 与后端枚举值一致
  APPROVED: '已通过',
}
```

> ⚠️ key 不一致会导致状态显示空白或错误。

## 10.5 通用

### 10.5.1 不要修改已执行的迁移文件

已执行的迁移文件（执行过 `alembic upgrade head` 的）禁止修改。需要的变更通过新增迁移实现。

**原因**：修改已执行的迁移会导致 `alembic history` 校验失败，开发环境和其他环境的数据库状态不一致。

### 10.5.2 生产环境 Swagger 必须关闭

`.env` 中 `DEBUG=false` 会隐藏 Swagger 文档。生产环境不要打开 `DEBUG`。

**原因**：Swagger 暴露了所有 API 端点和参数，是安全风险。调试时用本地环境。

### 10.5.3 Cookie/Token 不以明文存储

JWT Token 存储在 `localStorage`。注意：
- Token 过期时间默认 24 小时（配置：`JWT_EXPIRE_MINUTES=1440`）
- 不要在 URL 中传递 Token
- 不要在前端代码中硬编码密钥

### 10.5.4 异常日志要带上下文

❌ **错误做法**：

```python
except Exception as e:
    logger.error(f"操作失败: {e}")
```

✅ **正确做法**：

```python
except Exception as e:
    logger.error(f"入库单创建失败: [{order_no}] {e}", exc_info=True)
```

`exc_info=True` 会打印完整堆栈，方便定位问题。

## 10.7 Git 回溯规范

### 回溯触发条件

当**连续两次修复失败**（同功能点连续两次尝试后仍报错/失败）时，必须触发 Git 回溯流程：

1. **停止继续修复** — 不要再尝试第三次猜测修复
2. **执行** `git log --oneline -10` 查看最近提交记录
3. **找到最后一个稳定版本** — 即该功能开始前的那次提交
4. **执行** `git checkout [稳定版本]` 或 `git revert [问题提交]`
5. **在稳定版本上重新分析问题** — 重新调用 `systematic-debugging`

### 每次主线完成后

```bash
git tag -a v1.0-milestone-[字母] -m "主线[字母]完成：[简要描述]"
```

示例：
```bash
git tag -a v1.0-milestone-A -m "主线A完成：采购来料管理"
git tag -a v1.0-milestone-B -m "主线B完成：返厂维修"
```

| 里程碑 Tag | 备份动作 |
|-----------|---------|
| 打 Tag 后 | 执行数据库备份 `docker exec ims-db mysqldump -u root -p ims > backup_tag_$(date +%Y%m%d).sql` |

### 验证标准

- 每次主线完成后有对应 Tag
- 出现连续两次修复失败时，先回溯再分析，不继续猜测修复
